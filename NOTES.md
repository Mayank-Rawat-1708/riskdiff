# NOTES

What's broken, what was cut, and the calls I'd defend in a review.

## Known broken / weak

**The YAML handling is bespoke and will break if the schema grows.**
`server/src/repoManager.ts` and `agent/tools/scripts/backtest.mjs` both
hand-roll parsing restricted to exactly this ruleset's shape (flat
scalars, one nested `condition:` map, folded `>` descriptions). A real
`js-yaml` round-trip would be more correct but reformats the whole file
on write, which turns every one-line threshold change into a diff that
touches everything — and a readable diff is the entire point of this
product. Left it bespoke on purpose. If the schema grows past what
RULES.md item 2 keeps small, this is the first thing to replace, with a
comment-preserving YAML CST rather than a plain parse/dump.

**The backtest's frequency rule only understands a 10-minute window.**
The dataset precomputes `account_tx_count_10min`, so a proposal setting
`window_minutes: 30` gets evaluated against the 10-minute count. The
tool emits a warning saying so rather than silently returning a wrong
number, and the UI surfaces warnings verbatim, but the number is still
an approximation. Fixing it means computing windows from raw timestamps
at backtest time — maybe 30 minutes of work, cut because a *visible
wrong answer* was safer than an invisible one within the window.

**Conversation history is in-memory; git state is not.** If the server
restarts (Render free tier sleeps), open proposals are recovered from
their git worktrees on boot — branch, commits, and diff all survive —
but the turn-by-turn conversation that produced them is gone, and the
UI says so explicitly rather than pretending. The right fix is writing
turns into the proposal branch as a file, which would also make the
conversation itself diffable. That's the first thing I'd build with
more time.

**PAT embedded in the remote URL.** `authedRemote()` puts the GitHub
token into the remote URL, so it ends up in `.git/config` on the
runtime disk. Fine for a take-home on an ephemeral container, not fine
for production — a credential helper or a short-lived GitHub App token
belongs there instead.

**Script-hook stdin schema is an educated guess.** GitAgent's README
documents the *programmatic* hook context precisely (`ctx.toolName`,
`ctx.args`) but is less explicit about the JSON shape passed to
*script* hooks. `agent/hooks/guard-branch.sh` defensively reads
`toolName`, `tool`, and `tool_name`. This is why the same guard also
exists programmatically in `agentRunner.ts`, where the shape is typed
and certain — the shell version is a backstop for CLI use, not the
primary enforcement.

**Single active proposal in the UI.** The backend handles many
concurrent proposals (separate worktrees, a write lock on `main`); the
frontend only surfaces one. Cut for scope, not blocked by anything.

**No auth.** Anyone with the URL is "the analyst". Obviously wrong for
a tool that edits fraud policy; out of scope for the window.

## Deliberate cuts

- **No streaming.** The agent's response arrives all at once. Streaming
  would feel faster but adds SSE plumbing, and for a decision surface
  where you read the backtest before acting, a 6-second wait with
  honest status beats watching tokens land.
- **No auto-merge, ever.** There's no configuration for it and I didn't
  build one. A system whose value is "a human reviewed this" shouldn't
  ship a switch that turns that off.
- **Synthetic data only.** Obvious, but worth stating: `data/` is
  generated by `scripts/gen_transactions.py` with a fixed seed. Fraud
  correlates *imperfectly* with the signals on purpose — a clean 100%
  catch rate would make the backtest look impressive and mean nothing.
- **Left the workbench out of GitAgent's own voice/web UI at :3333.**
  The harness ships one. Using it would have satisfied "it runs on
  GitAgent" while failing the actual brief, which asks for an operating
  surface rather than a chat box.

## Calls worth defending

**Squash-merge instead of a merge commit.** One approved proposal =
one commit on `main`, whatever the agent's iteration history looked
like on the branch. It makes `git log` on the ruleset read as a policy
changelog rather than a transcript of the agent's false starts, and it
makes revert trivially a one-commit operation. The cost is that the
iteration history dies with the branch; I think a clean, auditable
policy log is worth more than preserved drafts, but it's a real
tradeoff and I'd reverse it if the team wanted to audit *how* the
agent got somewhere, not just where it landed.

**The agent's failures are UI, not logs.** A missing `COMMIT_MSG`, a
proposal with no backtest attached, files touched outside the ruleset,
a provider that fell over — each renders as a visible warning in the
workbench. The temptation with an agent product is to hide its
misbehavior so the demo looks smooth. For a tool whose job is
governing risk policy, an agent that quietly skipped its own rules is
precisely the thing the operator most needs to see.

**`compliance.human_in_the_loop: true` in `agent.yaml` is a claim the
code actually honors.** `DUTIES.md` spells out who holds which
authority, which is what that block is validated against. It would
have been easy to set the flag and not mean it.

## With a full week

1. Conversation turns committed to the proposal branch, so the
   reasoning is as diffable as the rule.
2. Real timestamp-window evaluation in the backtest, killing the
   10-minute approximation.
3. A branch-comparison view: two competing proposals for the same
   incident, backtested side by side, analyst picks one. The git model
   already supports this completely — it's purely UI.
4. Shadow mode: merge a rule to a `shadow` branch that scores live
   traffic without acting, promote to `main` after N days of real data.
   This is the feature the git-native design most obviously wants and
   the one I'd want to build most.
5. Auth, and a per-analyst identity on commits so `git blame` on the
   ruleset names a person.
